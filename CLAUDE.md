## Arbeitsregeln

- Dokumente, UI-Texte, Fehlermeldungen und Commit-Messages auf **Deutsch**; Code, Bezeichner und Datenfelder auf Englisch. In der Oberfläche erscheinen keine technischen Begriffe wie „ID“, „rev“ oder „IndexedDB“.
- **Umsetzungsstand nur in TDD Kap. 21** pflegen (🔲 offen · 🔶 in Arbeit · ✅ erledigt). Alle anderen Kapitel beschreiben den Sollzustand. Zurückgestellte Pakete wandern ans Ende von Kap. 21 unter „Zurückgestellt“ (mit Begründung und Anlass zur Wiederaufnahme), damit ihr Meilenstein abschließbar bleibt.
- IDs (FR, D, TAK, S …) werden nie neu vergeben; entfallene Einträge bleiben mit „entfallen“ stehen. Neue technische Entscheidungen bekommen eine D-Nummer in TDD Kap. 17, neue Arbeitspakete fortlaufende S-Nummern.
- Inhaltliche Änderungen an PRD/TDD erhöhen die Version im Dokumentkopf und bekommen eine Zeile in der Änderungshistorie (inkl. Spalte „Entstehung“ mit Modell). Commit-Messages nennen das Dokument und die Version, z. B. „PRD 2.4: …“.
- `docs/code-iteration1/` (per `.gitignore` ausgeschlossen) enthält den alten Prototyp mit **Lehrwerksvokabeln**. Diese Inhalte dürfen nicht in das Repository, in Fixtures oder in das Beispielset übernommen werden; das Repository ist öffentlich. Das Ablaufverhalten des Prototyps (z. B. Karteikarten-Warteschlange) darf als Vorlage dienen.
- **Das Repository ist öffentlich: keine privaten Details** in getrackten Dateien, Kommentaren oder Commit-Messages (Rechner- und Gerätemodelle, Vorfallzeiten, Home-Pfade, IPs, Zugangsdaten). Probleme der Umgebung neutral festhalten („Rechner überlastet“, Gegenmaßnahme); Geräte allgemein nennen (iPhone, iPad, Android-Smartphone).
- Schlank bleiben: **keine Laufzeitabhängigkeiten**, kein Framework, kein CDN (D-04). Neue Entwicklungsabhängigkeiten nur mit klarem Nutzen und Eintrag in TDD 4.1.
- **Diese Datei aktuell halten:** Neue Erkenntnisse, die künftigen Sitzungen helfen (geänderte Befehle, Stolperstellen, neue Konventionen, Abweichungen vom geplanten Stand), sofort hier ergänzen. Kurz bleiben: nur, was sich nicht schnell aus Code oder Dokumenten ergibt.
- **Rückschau nach jedem Arbeitspaket und jeder längeren Sitzung**, vor dem Abschlussbericht:
  1. Was hat Zeit gekostet oder überrascht (Fehlversuche, Werkzeugmacken, falsche Annahmen über Code oder Dokumente)? Was hat der Nutzer korrigiert oder ausdrücklich bestätigt? Würde das einer künftigen Sitzung helfen?
  2. Jede solche Erkenntnis an den passenden Ort schreiben: Befehle, Stolperstellen, Arbeitsweise → diese Datei; fachliche oder technische Klarstellungen → PRD, TDD oder Formatspezifikation (mit Version und Änderungshistorie); neue Entscheidungen → D-Nummer in TDD Kap. 17; Ergebnisse manueller Prüfungen → beim Arbeitspaket in Kap. 21.
  3. Diese Datei gegenlesen: Veraltetes korrigieren oder entfernen.
  4. Im Abschlussbericht in einem Satz nennen, was festgehalten wurde – oder dass es nichts Neues gab.

## Git-Ablauf

Diese Regeln gelten als Auftrag zum Committen und Mergen; gepusht wird nur auf ausdrückliche Anweisung.

1. **Branch anlegen:** Für jedes nicht-triviale Arbeitspaket (jedes S-xx, jede Änderung mit Code oder Tests, jede neue Dokumentversion) vor der ersten Änderung vom aktuellen `main` abzweigen: `git switch -c s-07-import-validierung` (mit S-Nummer `s-<nr>-<stichwort>`, sonst nur `<stichwort>`; klein, mit Bindestrichen). Direkt auf `main` nur Triviales, das in einen einzigen Commit passt und weder Code, Tests noch PRD/TDD berührt, z. B. Tippfehler, README, CLAUDE.md, `.gitignore`.
2. **Klein committen:** Auf dem Branch nach jedem in sich stimmigen Schritt committen, z. B. Test und Implementierung einer Funktion, ein Konfigurationsschritt, eine Dokumentanpassung. Message: eine Zeile, Deutsch, Infinitivstil wie „Kurzform beim Import auflösen“, ohne S-Präfix. `npm run typecheck` und `npm test` sind vor jedem Commit grün (testgetrieben: Test und Implementierung zusammen committen). Dateien gezielt stagen (`git add <pfad>`), kein `git commit -a` und kein `git add -A`, solange noch andere Änderungen offen sind; vor dem Commit `git diff --cached --stat` prüfen. Sonst landen unfertige Änderungen im falschen Commit, und nach einem Push hilft kein Amend mehr.
3. **Abschließen mit Squash-Merge:** Wenn das Paket fertig ist – Akzeptanzkriterien erfüllt, `typecheck`, `test`, `build` und bei UI-Änderungen `test:e2e` grün, Status in TDD Kap. 21 noch auf dem Branch auf ✅, Rückschau (siehe Arbeitsregeln) auf dem Branch erledigt:

   ```bash
   git switch main
   git merge --squash s-07-import-validierung
   git commit                               # Message siehe unten
   git branch -D s-07-import-validierung    # -D nötig: Squash markiert den Branch nicht als gemergt
   ```

   Auch ohne eigenen Worktree committen parallele Sitzungen auf `main` (20.11.2026: TDD-Version belegt, Squash-Merge mit Konflikt): Vor `git switch main` mit `git log -1 main` prüfen, ob `main` noch der Abzweigpunkt ist; sonst erst `git rebase main` auf dem Branch, Dokumentversion neu wählen, dann mergen.

   Message wie bei `4c3494b`: Betreff `S-07: <Zusammenfassung> (TDD 2.3)` (Dokumentversion nur, wenn sie erhöht wurde), darunter eine knappe Stichpunktliste der wesentlichen Änderungen.

   **In einer Worktree-Sitzung** (z. B. Hintergrundjob): `EnterWorktree` legt den Branch als `worktree-<name>` an – gleich in `s-<nr>-<stichwort>` umbenennen. Er zweigt von `origin/main` ab; ungepushte Commits des lokalen `main` fehlen dann. Soll eine neue Sitzung einen Worktree einer beendeten fortsetzen und `EnterWorktree` meldet „belongs to another running Claude Code session“ (der Prozess der beendeten Sitzung lebt noch, ihr Job steht in `~/.claude/jobs/<id>/state.json` auf `done`), vorher im Hauptverzeichnis `git worktree unlock .claude/worktrees/<name>`. Vor der ersten Änderung `git log -1` mit `git log -1 main` vergleichen und den noch leeren Branch mit `git reset --hard main` nachziehen. Ein neuer Worktree hat kein `node_modules`: zuerst `npm ci`. Die Sitzung lehnt Shell-Befehle ab, die sie nicht als Git-frei erkennen kann (Heredocs – `python3 - <<'EOF'` ging in S-29, mit `cd` davor nicht –, Shell-Variablen als Argument (auch `$CLAUDE_JOB_DIR`; den Pfad ausschreiben), `xargs` vor `sed`, schon Wörter wie „digit“, Text, der Git-Befehle nennt, oder eine URL mit „github“ wie bei `curl` auf die Live-App); Dateien dann mit Edit/Write ändern, Befehle aufteilen; mehrere Ersetzungen oder Gegenproben als Skriptdatei im Job-Verzeichnis (`…/jobs/<id>/tmp/`) ablegen und mit `python3 <datei>` bzw. `zsh <datei>` ausführen – das wird angenommen (in zsh keine Variable `path`, sie ist an `PATH` gekoppelt; Globs als Argument quoten, `grep --include=*.ts` bricht sonst mit „no matches found“ ab). Aus dem Worktree heraus sind Git-Befehle auf das Hauptverzeichnis gesperrt (`git -C`, `main` ist dort ausgecheckt), und Edits im gemeinsamen Checkout werden abgelehnt. Offene Änderungen eines parallelen Worktrees mit `git -C .claude/worktrees/<name> status` bzw. `diff` ansehen, nicht per `cd` hinein: Die Sitzung übernimmt sonst dessen Verzeichnis als Arbeitsverzeichnis (S-38). `cp` und `rm` fragen in der Shell nach (Alias `-i`) und brechen ohne Eingabe ab, `rm` dabei ohne Fehlermeldung; für Gegenproben die Änderung mit `sed` zurücknehmen oder `/bin/cp` bzw. `/bin/rm` nutzen. Parallele Sitzungen committen derweil auf `main`, oft in TDD Kap. 21 und dieser Datei, und belegen dabei auch Dokumentversionen, D- und E2E-Nummern: Die eigenen Nummern erst nach dem Nachziehen wählen, dabei auch noch nicht gemergte Branches ansehen (`git show <branch>:docs/TDD_Vokabeltrainer_Allgemein_v2.md`), und beim Rebase prüfen, ob sie noch frei sind. Deshalb zum Abschluss: im Worktree `git rebase main`, Konflikte dort lösen, Prüfungen wiederholen; dann `ExitWorktree` mit „keep“ und im Hauptverzeichnis `git merge --squash`, `git commit`, `git worktree remove .claude/worktrees/<name>`, `git branch -D`. Kurz vor dem Merge noch einmal `git log -1 main` prüfen.

   **Parallele Pakete:** Ändert ein parallel laufendes Paket dieselben Dateien oder Zentrales (z. B. `vite.config.ts`, Empty State, gemeinsame Tests), will der Nutzer dessen Merge abwarten und die eigenen Änderungen dann verwerfen und auf dem neuen Stand neu umsetzen statt mergen (S-16). Wiederverwendbare Inhalte (z. B. Datendateien) vorher im Job-Verzeichnis sichern. Eine Hintergrund-Warteschleife auf `main` überlebt einen Neustart der Sitzung nicht (Exit -1); danach `git log main` selbst prüfen.

4. **Deployen (D-21):** Online geht nur, was auf `production` liegt; `production` entsteht ausschließlich per Fast-Forward aus `main`. Nur auf ausdrückliche Anweisung und erst, wenn die CI für `main` grün ist: `git push origin main:production` (lokales `main` vorher auf `origin/main`). Nie direkt auf `production` committen, nie force-pushen.

Eingerichtet (S-01, S-02, S-05):

```bash
npm run dev          # Vite-Dev-Server (Service Worker deaktiviert); `?testmigration=ok|fail` prüft die Test-Migration (Kopie in `vokabeltrainer-testmigration-premigration`; der `TypeError` in `setSize` bei `ok` kommt vom Test-Set ohne Sektionen), `?perf` misst TAK-15 (TDD 15.6)

npm run preview      # gebautes Artefakt lokal ausliefern (Port 4173)
npm run typecheck    # tsc -b über die Projektreferenzen; `tsc --noEmit` im Wurzelverzeichnis prüft nichts; „Cannot find module“ nach einem Merge mit neuer Abhängigkeit: erst `npm ci`
npm run format       # Prettier (Markdown ist ausgenommen, Dokumente werden von Hand formatiert)
npm run icons        # PNG-Icons aus public/icons/icon.svg neu erzeugen (Playwright-Chromium), Ergebnis einchecken
npm test             # Vitest-Projekt `unit`: src/**/*.test.ts in Node
npm run test:e2e     # Playwright, Projekte mobile-chromium und mobile-webkit; baut selbst und startet `vite preview` auf Port 4180

npx vitest run src/domain/validate.test.ts      # einzelne Testdatei
npx vitest run -t "Kurzform"                    # Tests nach Name
npx vitest run --project build                  # nur Build-Prüfung gegen vorhandenes dist/
npx playwright test --project=mobile-webkit -g "Startseite"
```

Einmalig pro Rechner: `npx playwright install chromium webkit` (Browser für E2E, liegen im gemeinsamen Cache unabhängig von der Node-Version). Einmal pro installierter Node-Version (asdf): `npm i -g @playwright/cli` (Browserprüfung durch den Agent; Skill liegt unter `.claude/skills/playwright-cli/`, Aktualisierung mit `playwright-cli install --skills`). Meldet asdf „No version is set for command playwright-cli“, fehlt das Paket unter der aktiven Node-Version (z. B. nach einem Sicherheitsupdate von Node): dort neu installieren, nicht per `ASDF_NODEJS_VERSION` auf eine ältere Version ausweichen. Prüfung z. B. mit `npm run preview` und `playwright-cli open --mobile http://localhost:4173/`; Ausgaben landen in `.playwright-cli/`. In Skripten unter macOS markiert `Control+A` nicht alles (springt an den Zeilenanfang): Felder mit `fill` setzen. `playwright-cli` bringt eine eigene Playwright-Version mit und nutzt Chromium; für `--browser=webkit` einmalig `playwright-cli install-browser webkit`. Ohne diese Installation geht WebKit auch über ein kurzes, nicht eingechecktes Node-Skript im Projekt (`import { devices, webkit } from "@playwright/test"`, nutzt die Browser der E2E-Tests). CPU-Drosselung in Chromium per `run-code`: `page.context().newCDPSession(page)`, dann `Emulation.setCPUThrottlingRate`; sie bremst nur die Seite, nicht das Lesen aus IndexedDB. In Worktree-Sitzungen lehnt Claude Code `playwright-cli eval` ab; dann Code als Datei mit `playwright-cli run-code --filename=<datei>` ausführen (Inhalt `async (page) => …`, ohne abschließendes Semikolon). `run-code` gibt erst das Ergebnis, dann den ausgeführten Code aus: mit `head` lesen, nicht mit `tail`. Bleibt eine Sitzung mit geändertem Formular offen, blockiert die `beforeunload`-Rückfrage jeden weiteren Befehl („does not handle the modal state“): `playwright-cli dialog-accept`, dann `close`. Dasselbe gilt für Befehle mit JSON-Text als Argument (z. B. `fill`): Eingaben und Messungen in die Skriptdatei legen. Brechen alle Browser beim Start ab, auch ohne Sandbox (Chromium mit `mach_port_rendezvous … bootstrap_check_in … (141)`, auch `playwright-cli open` und das MCP-Plugin, WebKit mit `Abort trap`), ist das System nach einem Ruhezustand des Laptops in einem ungültigen Zustand: nicht umgehen, sondern den Nutzer um einen Neustart bitten. Notbehelf für Chromium bis dahin: `chromium.launch({ args: ["--single-process"] })` in einem Node-Skript (Import aus `node_modules/@playwright/test/index.mjs` per absolutem Pfad) mit `dangerouslyDisableSandbox`.

**Service Worker beim lokalen Prüfen:** `vite preview` (4173) registriert ihn, der Dev-Server nicht. Nach einem neuen Build zeigt ein schon geöffneter Browser auf 4173 weiter den alten Stand, bis man „Jetzt aktualisieren“ wählt. Das gilt auch für eine offene `playwright-cli`-Sitzung (mehrere `run-code` nacheinander): Nach einem neuen Build erst `playwright-cli close`, dann neu `open`; ohne `--persistent` startet sie dann leer. Umgekehrt behält eine offene Sitzung ihre Daten: Ein zweites `run-code`, das mit leerer Bibliothek rechnet, scheitert – vorher `close` und neu `open`. Der E2E-Update-Test startet eigene Preview-Server auf Ports ab 4280 (neue Testports nicht aus der „bad ports“-Liste des Fetch-Standards wählen, z. B. 4190 – WebKit lädt dort nichts).

In parallelen Sitzungen einen eigenen Port nehmen (`npx vite preview --port 4175 --strictPort`), 4173 ist oft belegt. `npm run test:e2e` nutzt fest Port 4180: Läuft die Suite schon in einer anderen Sitzung, bricht sie mit „http://localhost:4180/ is already used“ ab. `playwright test --ui` hält den Port dauerhaft; dann nicht warten, sondern eine nicht eingecheckte Konfiguration mit anderem Port nutzen (`playwright.port.config.ts`: `import base from "./playwright.config"`, `use.baseURL` und `webServer` auf z. B. 4182 umstellen; `npx playwright test -c playwright.port.config.ts`) und vor dem Commit löschen. Auch dann teilen sich parallele Läufe die Ports des Update-Tests (ab 4280): Scheitert nur `update.spec.ts`, ihn einzeln wiederholen.

**Systemlast:** Mehrere parallele Playwright-Läufe, vor allem mit WebKit, haben den Entwicklungsrechner überlastet (WindowServer reagierte nicht mehr, Neustart nötig). Die Ursache ist nicht gesichert. Gegenmaßnahmen: `workers` ist lokal 2 (CI 1); lokal im Alltag nur `npx playwright test --project=mobile-chromium` bzw. gezielt eine Datei, `mobile-webkit` nur in der vollständigen Suite vor dem Squash-Merge; höchstens ein vollständiger Lauf gleichzeitig auf dem Rechner; das Plugin `playwright` (MCP-Server, einer pro Sitzung) ist in den Claude-Code-Einstellungen des Nutzers abgeschaltet, Browserprüfung läuft über `playwright-cli`. Vorher `uptime` ansehen: Bei Load über 8 warten, auch statt eines Ausweichens auf einen anderen Port. Stürzen Browser beim Start ab, zuerst nach `.spin`-Berichten der Systemdiagnose sehen. Gegenprobe offen: Bleiben die Hänger ohne WebKit aus, ist es der Auslöser.

Nach UI-Änderungen das Verhalten mit `playwright-cli` gegen Dev-Server oder `vite preview` prüfen und die E2E-Smoke-Tests laufen lassen.

**Messen unter Last (S-49):** Laufen parallel E2E-Tests anderer Sitzungen (`uptime` zeigt Load 20–60), schwanken `?perf`-Werte um das Mehrfache (Lesen 2–7 s statt 0,5 s). Dann eine Änderung nur relativ bewerten: dieselbe Messung direkt davor und danach ohne die Änderung, oder eine nicht eingecheckte Vitest-Datei mit `perfHistory` aus `src/dev/perfData.ts` und `--silent=false` (sonst fehlt `console.log`).

**Messen auf dem Gerät (S-24):** Dev-Server aus dem eigenen Worktree mit `npx vite --host --port 5179 --strictPort` starten (Hintergrund), der Nutzer öffnet `http://<Mac-IP>:5179/?perf` im selben WLAN (`ipconfig getifaddr en0`). Ohne HTTPS ist dort die Zwischenablage gesperrt, und `crypto.randomUUID` fehlt; der Nutzer kopiert das Ergebnis per Markieren. Der Nutzer misst auch mit Firefox; den Browser aus der Kennung im Ergebnis ablesen, nicht annehmen.

## CI und Deployment (S-03, S-04, TDD 4.4, 4.5)

`.github/workflows/ci.yml` läuft bei jedem Push (jeder Branch) und Pull Request: Job `check` (`npm ci` → `format:check` → `typecheck` → `test` → `build`) und parallel Job `e2e` als Matrix je Browser (`--project=mobile-chromium` bzw. `mobile-webkit`, je Browserinstallation und `test:e2e`, Limit 25 Minuten; zuvor ein Job mit 15 Minuten, den die gewachsene Suite fast gerissen hätte). Nur bei Push auf `production` folgen Upload von `dist/` (aus dem Chromium-Lauf) und Job `deploy` (prüft, dass der Commit in `main` liegt) nach https://vokabeltrainer.cgrothaus.de/ (eigene Domain in den Pages-Einstellungen, keine Datei `CNAME`, TDD 4.4; die frühere Adresse https://cgrothaus.github.io/vokabeltrainer/ leitet dorthin um). Die Umgebung `github-pages` lässt nur `production` zu; ein Ruleset verbietet dort Force-Push und Löschen. Lokal nachstellen mit denselben Befehlen und `CI=1` vor `npm run test:e2e` (`github`-Reporter; wie die CI zwei Worker, am besten mit `--project=…`). Läufe verfolgen mit `gh run watch`; scheitern `gh` („error connecting to api.github.com“, kein Token) und `git` über SSH („No user exists for uid 501“) zugleich, sind DNS und Verzeichnisdienst des Systems ausgefallen (Neustart nötig); den Status liest bis dahin `curl --resolve api.github.com:443:<IP aus dig @1.1.1.1>` ohne Sandbox, Annotationen unter `check-runs/<job-id>/annotations`. E2E-29 (Ziehen am Griff) war in `mobile-webkit` auf der CI schon einmal unregelmäßig rot; bei Fehlern liegt der Playwright-Report als Artefakt `playwright-report-<projekt>` am Lauf (`gh run download <id> -n playwright-report-mobile-webkit`). Die Playwright-Version steht nur in `package.json` (kein Container-Image, kein Browser-Cache).

## Architektur (Soll, TDD Kap. 3–7)

**Auslieferung:** eine `index.html` mit eingebettetem JS und CSS (`vite-plugin-singlefile`) plus `sw.js`, `manifest.webmanifest` und Icons. Alle Verweise relativ (läuft unter GitHub-Pages-Unterpfad und eigener Domain). Manifest und Icons liegen in `public/`; in `index.html` mit Wurzelpfad verweisen (`/manifest.webmanifest`), Vite macht daraus `./…`. Build zweistufig: `vite build` → `vite build -c vite.sw.config.ts`; `scripts/precache.ts` liefert Dateiliste und Cache-Version (Hash über alle vorab gespeicherten Dateien), damit sich `sw.js` genau dann ändert, wenn sich eine davon ändert. Neue Dateien, die offline nötig sind, dort aufnehmen. Formatspezifikation und Schema veröffentlicht ein Plugin in `vite.config.ts` aus `docs/` neben der App (`PUBLISHED_DOCS` in `scripts/precache.ts`, D-26); jede Änderung an der Spezifikation ist damit eine neue App-Version, und ihr Beispiel aus Kap. 1 muss wörtlich zu `src/content/help.ts` passen (`tests/format/help.test.ts`). Die Spezifikation ist ein ausgeliefertes Dokument (D-35): keine Verweise auf PRD, TDD oder IDs wie FR-/S-/D-Nummern, keine Prompt-Vorlage (die steht nur in `help.ts`); derselbe Test wacht darüber. Rückverfolgung zu den Anforderungen in TDD Kap. 8. Sie beschreibt Kontext und Bedeutung statt Anweisungen; Kapitelnummern stabil halten, Code und TDD zitieren sie. `vite preview` liefert `.md` ohne Zeichensatz aus; das Plugin setzt `charset=utf-8` wie GitHub Pages. Deployment auf GitHub Pages nur vom Branch `production` nach grüner CI.

**TypeScript 7** (native `tsc`), Konfiguration über Projektreferenzen: `tsconfig.app.json` (`src/` ohne `src/sw`, DOM), `tsconfig.sw.json` (`src/sw`, WebWorker), `tsconfig.node.json` (Vite-Konfigurationen, `scripts/precache.ts`), `tsconfig.test.json` (`tests/`, `scripts/`), `tsconfig.domain.json` (`src/domain` ohne DOM- und Node-Typen, TAK-04; `tsconfig.app.json` prüft `domain/` zusätzlich mit). Kein `enum`, kein `namespace`, keine Parameter-Properties im Konstruktor (`erasableSyntaxOnly`). Verzeichnisse aus TDD 3.1 entstehen erst mit ihrer ersten Datei.

**Gestaltung (M5):** Soll in TDD 13.7 (D-45). Vorlage ist ein klickbarer Entwurf als privates claude.ai-Artifact (Link in 13.7): eine HTML-Datei, Quelle mit dem Artifact-Werkzeug (`action: "read"`) holen, Änderungen am Entwurf mit `url` veröffentlichen. **Schichten unter `src/`** – die Importrichtung ist hart:

- `domain/` – reine Funktionen (Validierung, Normalisierung, Diff/Merge, Übungslogik, Statistik, Migrationen). Importiert nichts aus `app/`, `storage/`, `platform/` und nutzt kein `window`, `document` oder `indexedDB` (TAK-04). Auch `crypto` fehlt dort (gilt ebenso für Tests in `src/domain`): Zufall wird als `RandomBytes` übergeben (`domain/ids.ts`, App: `platform/random.ts`), zum Mischen als `random: () => number` (App: `Math.random`); Tests nutzen eine feste oder seeded Folge; eine Folge mit kurzer Periode (z. B. `counter++ % 31`) taugt nur für wenige IDs, bei Sets mit Dutzenden Einträgen zieht `freshId` sonst endlos neu (dann `crypto.getRandomValues` in Tests außerhalb von `src/domain`). Ohne DOM-Typen gibt es dort auch kein `structuredClone`.
- `storage/` – IndexedDB; kennt `domain/model.ts`, aber keine UI. Geöffnet wird nur über `openDatabase` (`storage/database.ts`, liefert ein Ergebnis pro Fehlerlage statt zu werfen), geschrieben nur über `runTransaction` (`storage/transaction.ts`, erfüllt erst nach `complete`). `runTransaction` legt die Transaktion synchron an und führt `work` sofort aus (kein `await` dazwischen, sonst kann sie inaktiv werden). Ist die Verbindung verloren, öffnet `storage/connection.ts` sie vorher neu, aber nur für Verbindungen, die `main.ts` mit `keepConnected` angemeldet hat, und nur, solange `work` noch nicht lief (D-32); Tests mit `db.close()` scheitern deshalb weiter wie erwartet. Neue Sets mit `addSet` (`add()`, nie `put()`); eine bekannte Set-ID geht in den Abgleich (unten). Änderungen an einem vorhandenen Set nur mit `updateSet(db, set, expectedEditCount, now)`: liest in derselben Transaktion und schreibt nur, wenn `editCount` noch stimmt (`changed` sonst); die Änderung selbst rechnen reine Funktionen in `domain/editSet.ts`. Sitzungen und Antworten über `storage/sessions.ts`. Ein Upgrade mit Datenumwandlung bricht `openDatabase` zuerst ab, sichert den Altstand in `<name>-premigration` (`storage/preMigrationCopy.ts`, 14 Tage über `meta.preMigrationCopyAt`) und öffnet erneut (TDD 7.3). `deleteSet` löscht Sitzungen und Events des Sets mit (D-25): `validateRecords` lehnt Verweise auf fehlende Sets ab, verwaiste Datensätze machten jedes Backup ungültig.

Den Inhalt deshalb vor dem Tippen fertigstellen (die Backup-Ansicht liest beim Öffnen) und im Klick ohne vorheriges `await` aufrufen.

Routen sind Muster: feste Teile und `*` für genau einen nicht leeren Pfadteil (`/import`, `/set/*`, `/entry/*/*`); die Ansicht bekommt die Teile als Parameter (`(signal, ...params)`). In Kommentaren `/**/` meiden: `*/` im Muster beendet den Kommentar. Der Router gibt jeder Ansicht ein `AbortSignal`, das beim Verlassen abbricht (zum Aufräumen, z. B. Sitzung beenden). Sie steht in der App-Leiste: Jede Ansicht gibt `frame(options, main).element` zurück (`components/frame.ts`, TDD 13.7) mit `back: { parent }` (übergeordnete Ansicht, falls es im Verlauf nichts davor gibt), `actions` (Symbolknöpfe, `iconLink`, Symbole aus `app/icons.ts`) und `dock` (Hauptaktion unten; ein Submit-Knopf dort braucht das Attribut `form`); wer nachlädt, ruft `setTitle`, `setBack`, `setDock` später. Formulare mit Textfeldern bekommen keine Aktionsleiste (D-49). Rückfragen als Blatt mit `openSheet(page.element, { title, content, focus, returnTo, onDismiss })` (`components/sheet.ts`): `close()` nach einer Wahl, `dismiss()` wie Escape. Wer selbst fokussieren will (Meldung, Karte), tut das mit `focusSoon` (`app/dom.ts`) beim Aufbau, dann bleibt es dabei. Kein eigenes `focus()`-Hilfsstück mehr in Ansichten. Die laufende Lernsitzung lebt nur im Arbeitsspeicher (`currentPractice()`); nach dem Neuladen leitet `#/practice` zur Bibliothek. **Querschnittsregeln, die leicht übersehen werden:**

- Daten werden **nie** über `innerHTML` eingefügt; Strings im DOM-Helfer sind immer Textknoten (TAK-03). Kein `eval`/`new Function`. Keine Netzwerkanfragen außer an eigene statische Dateien.
- Fachliche Änderungen über mehrere Datensätze/Stores laufen in **einer** Read-Write-Transaktion; „gespeichert“ erst nach `transaction.oncomplete`.
- Speicherfehler (TDD 6.5, D-32): eingeordnet in `storage/errors.ts` (`quota`, `connection`, `failed`), Meldungen nur über `storageMessage`/`failureMessage` aus `app/storageMessages.ts`, nie als eigene Texte. Ein Schreibvorgang ohne eigene Meldung am Ort (im Hintergrund) meldet sich mit `reportStorageProblem` aus `components/storageNotice.ts`, statt nur in die Konsole zu schreiben.
- Mehrere Tabs (TDD 3.4, D-43, D-48): Die Nachricht an andere Tabs sendet `main.ts` zentral aus `onSaved` (Stores der Transaktion: bei `sets` oder `settings` `data-changed`, sonst bei `reviewEvents` `answers-recorded`, das drüben nur den Lernstand-Zwischenspeicher verwirft); Abläufe senden nichts selbst. Neu gezeichnet werden nur die Muster in der Liste am Ende von `startRouter(…)` in `main.ts`; aufklappbare Abschnitte bleiben dabei nur mit `id` offen. Wer zu einem Set schreibt, ohne `updateSet` zu nutzen (das `editCount` prüft), prüft dessen Existenz in derselben Transaktion (`writeIfPresent` in `storage/sessions.ts`, `SetMissingError`); Storage-Tests für Sitzungen und Antworten legen deshalb vorher Set und Sitzung an.
- Ein Set ist **ein Dokument** im Store `sets` (Sektionen und Einträge eingebettet, Reihenfolge = Array-Reihenfolge). Lernstand wird nur aus `reviewEvents` berechnet (`domain/stats.ts`, Zählregeln TDD 12.6, D-30); es gibt keinen `progress`-Store. `loadOverview` (`app/overview.ts`) behält das Ergebnis pro Set und `editCount` im Arbeitsspeicher (S-38, D-48): Wer Antworten schreibt oder löscht, ruft danach `forgetOverview(setId)` bzw. `forgetAllOverviews()`; Tests mit `loadOverview` leeren ihn im `beforeEach`.
- Präferenzen pro Set liegen in `settings` unter `<art>:<setId>` (bisher `practice:<setId>`, `settingKey` in `domain/practiceSetup.ts`) und gehören ins Backup. `deleteSet` muss jeden solchen Schlüssel mitlöschen. Globale Präferenzen haben keinen Doppelpunkt (bisher `theme`, `domain/theme.ts`, und `speakAloud`, `domain/speech.ts`); `deleteSet` lässt sie stehen, nur „Alle Daten löschen“ (`clearAllData`) leert `settings` ganz. Werte beim Lesen tolerant prüfen (sie können aus einem Backup stammen), `validateRecords` prüft in `settings` nur `key`.
- Intern immer Langform (`{ text, acceptedVariants? }`); Kurzformen aus Dateien werden beim Import aufgelöst, beim Export wieder geschrieben. Importablauf: `readSetFile` in `domain/importSet.ts` (herauslösen → `validate`), dann je nach Set-ID neues Set (`newSetFromFile`: `normalize` → IDs, `domain/duplicates.ts`) oder Abgleich mit dem vorhandenen (`domain/diff.ts` über `normalizeImportFile`, das `null` als Löschmarkierung behält; `domain/merge.ts` setzt mit den Entscheidungen um). `app/importText.ts` in zwei Schritten: `previewImport` schreibt nichts (`kind: "new"` bzw. `"known"` mit beiden Abgleichen), `saveImport` bzw. `saveKnownImport` (über `updateSet`, bei veraltetem `editCount` neue Vorschau) speichert nach Bestätigung; danach wechselt die App zur Bibliothek bzw. zur Set-Ansicht, die Meldung holt sie dort per `takeMessage` ab. Abgleichs-Tests bauen ihre Dateien mit `exportSetFile` und lesen sie mit `readSetFile`, damit `rev` stimmt. Fehlt in einer Datei ein vorderer Eintrag, rückt er beim Aktualisieren ans Ende (TDD 9.3): Das ist eine Umstellung, keine „keine Änderung“. Das Beispielset (`src/content/beispielset.json`, per `?raw` als Text eingebettet) läuft über denselben Weg ohne angezeigte Vorschau (`app/sampleSet.ts`) und öffnet danach die Set-Ansicht; es ist zugleich Fixture in `tests/format/setfile.test.ts`. Meldungen sind deutsche Strings mit Fundstelle. `validateSetFile` prüft die Datei unabhängig vom Ziel; was vom Ziel abhängt (Teil-Export bei neuem Set, Scope-Abgleich), gehört in den Ablauf (`newSetFromFile`, `diff.ts`).
- Ein neues Feld im Set-Format braucht drei Stellen: Feldtabelle bzw. `KNOWN_FIELDS` in `domain/validate.ts`, `docs/vokabeltrainer-set.schema.json` und die Formatspezifikation. Ein Test vergleicht Schema und `KNOWN_FIELDS`. Leere optionale Felder entfernt `normalize` ohne Warnung (D-24), leere Listenelemente sind Fehler.
- Unsichtbare Zeichen (BOM, kombinierende Zeichen) im Quelltext als `String.fromCharCode(0x…)` schreiben: `\uXXXX` landete beim Schreiben von Dateien schon als echtes, unsichtbares Zeichen.

- Migrationen sind reine Funktionen pro Datensatz in `domain/migrations/` (`migrateRecord`) und werden sowohl im `upgradeneeded`-Handler als auch beim Wiederherstellen älterer Backups verwendet. Struktur (Stores, Indizes) steht pro Version in `storage/schema.ts`; jede Version ab 2 braucht zusätzlich einen Eintrag in der Kette, auch ohne Datenänderung. Seit der ersten Auslieferung (S-29) ist das Datenmodell eingefroren: Jede Änderung am Gespeicherten (auch neue Pflichtfelder oder Indizes) erhöht `DB_VERSION` und braucht Schritt, Migration und neue Fixtures `tests/fixtures/{db,backup}/vN.json` aus der App; die erste (Version 2) außerdem E2E-04 (S-10). `tests/format/fixtures.test.ts` scheitert sonst. Die Fixtures entstehen wie v1 (TDD 15.3) mit einem nicht eingecheckten Playwright-Test im Job-Verzeichnis: dort `node_modules` als Symlink auf das Projekt, `support.ts` per absolutem Pfad importieren, eigene Konfiguration mit `webServer.cwd` auf den Worktree und eigenem Port; aufrufen mit `npx playwright test -c <konfiguration>`. Prettier lässt beide Verzeichnisse aus (bytegenau). Die Test-Migration v1 → v2 (`testMigration.ts` in `domain/migrations/` und `storage/`) gehört nie in die Kette der App. Fixtures früherer Stände unter `tests/fixtures/` werden nie gelöscht.
- Eine neue App-Version wird nie während einer Lernsitzung oder Bearbeitung aktiviert (TAK-12): Sitzung und Editor rufen dafür `setUpdateBlocked(true/false)` aus `app/components/updateNotice.ts` auf (Sitzung in `views/practice.ts`, Formulare über `guardUnsaved`).
